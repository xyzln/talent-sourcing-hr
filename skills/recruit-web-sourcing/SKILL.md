# 岗位设计研究与智能体生成工作流

## 用途

把「我想造个 agent，但不知道怎么设计」变成一份能直接落地的智能体设计规格：先研究现实中对应岗位是怎么设计的，再把岗位设计逐项翻译成 agent 设计，最后用覆盖度评分验证设计完整性。

## 使用时机

- 用户说「不知道怎么做个 agent / 子 agent / 技能」，或问「这个 agent 该怎么设计」
- 用户描述了想让 agent 做的事，但给不出结构化的设计
- 用户想把某个现实岗位 / 角色变成一个 agent
- 用户需要为专家包、独立技能或子智能体生成设计规格

## 五步流程

### 第 1 步：需求澄清

确认四件事，缺失信息先提问，不假设：

- **用途**：这个 agent 要干什么活？替谁干？给谁用？
- **场景**：典型任务与输入输出是什么？
- **形态**：落地为专家包 / 独立技能 / 子 agent（决定规格格式与启用方式）
- **边界**：明确不做什么、有哪些红线

### 第 2 步：现实岗位设计研究

全网检索现实中对应岗位是怎么设计的，采集六大要素。方法与渠道见 `references/search-playbook.md`：

- **职责**：这个岗位上的人具体干什么（拆到可执行的动作项）
- **任职要求**：靠什么胜任（知识、技能、经验、资质）
- **工作流**：真实的工作步骤、顺序与检查点
- **协作界面**：跟谁打交道、交接什么、输出给谁
- **考核指标**：怎么算干得好（质量、效率、结果标准）
- **工具栈**：用什么工具、系统、方法干活

检索纪律：每轮记录检索式、渠道、命中数、信源质量与获取时间；同一结论至少两个独立信源交叉验证；查不到就如实说明并给扩搜建议，不编造。

### 第 3 步：岗位 → 智能体映射

把岗位设计要素逐项翻译成 agent 设计要素，映射规则见 `references/capability-matching-model.md`：

| 岗位要素 | Agent 设计要素 |
|---------|--------------|
| 角色定位 | frontmatter description 与人格段落 |
| 职责 | 技能清单与工作流步骤 |
| 任职要求 | 能力锚定、筛选标准与边界铁律 |
| 工作流 | 工作流步骤与检查点 |
| 协作界面 | 输入输出规格与交接协议 |
| 考核指标 | 验收标准与质量门槛 |
| 工具栈 | 工具与脚本清单 |

每项映射都必须能回溯到第 2 步的岗位研究证据；岗位上没有的要素，agent 也不许有。

### 第 4 步：设计覆盖度评分

1. 把 agent 设计拆成 5-8 个可评分维度（人格定位、职责覆盖、工作流完整、协作界面、验收标准、工具齐备、边界清晰等）
2. 按 0-5 级锚定量表对照岗位研究证据打分，无证据不评分
3. 运行 `scripts/match_score.py` 计算加权覆盖度（输入评分 JSON，输出总分、分级、强覆盖项、缺口项与一票否决标记）
4. 评分模型、锚定示例与分级标准见 `references/capability-matching-model.md`
5. 有缺口的维度，回到第 3 步补设计或回第 2 步补研究，再重评

### 第 5 步：Agent 规格生成

按 `references/report-template.md` 输出完整规格：结论先行（这个 agent 是什么、岗位依据、覆盖度分级）、岗位设计研究摘要（六要素 + 信源）、Agent 设计规格（frontmatter、人格、技能、工作流、工具、边界铁律、验收标准）、覆盖度明细与缺口补齐建议、落地方式（专家包 / 技能 / 子 agent）与启用步骤。结尾给用户 3 个可立即执行的下一步动作。

## 铁律

- 岗位设计研究只依据公开可查信源（JD、组织设计资料、行业报告、从业者分享），所有结论标注信源与获取时间，不编造
- agent 的每项设计必须来自岗位研究证据，不凭空发明能力
- 不设计用于作弊、欺诈、歧视、绕过监管或侵犯隐私的 agent
- 覆盖度评分只基于证据，无证据 = 0 分并标注「待验证」
- 需求不清先提问，不在错误假设上生成设计
