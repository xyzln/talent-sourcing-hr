# نموذج تحويل الوظيفة إلى تصميم الوكيل

> يُستخدم في الخطوتين 3 و4 من مهارة `recruit-web-sourcing`. الهدف: ترجمة «تصميم الوظيفة» إلى «تصميم الوكيل»، والتحقق من اكتمال التصميم بتقييم تغطية قابل للإعادة.

## 1. عناصر تصميم الوظيفة → عناصر تصميم الوكيل

| عنصر تصميم الوظيفة | عنصر تصميم الوكيل | موضع التطبيق |
|---------------------|-------------------|--------------|
| الدور (لماذا هذه الوظيفة) | تمركز الوكيل | frontmatter description + مطلع الشخصية |
| المسؤوليات (ما يفعله) | قائمة المهارات وخطوات سير العمل | مصفوفة skills + قسم سير العمل |
| المتطلبات (ما يجعله كفؤًا) | مراسي القدرات والخطوط الحمراء | قدرات الشخصية الأساسية + القواعد الحاكمة/الملاحظات |
| سير العمل (كيف وبأي ترتيب) | خطوات سير العمل ونقاط التحقق | قسم سير العمل (لكل خطوة إجراءات ومخرجات) |
| التعاون (مع من يتعامل) | مواصفة المدخلات والمخرجات وبروتوكول التسليم | مواصفة المخرج + شروط التشغيل/الخروج |
| المؤشرات (ماذا يعني «أُنجز بشكل جيد») | معايير القبول ومستويات الجودة | خط القبول في مواصفة المخرج |
| الأدوات (بما يعمل) | قائمة الأدوات والسكربتات | scripts/ + الأدلة المرجعية + ملاحظات الأدوات |

**قواعد التحويل**:
- العناصر الحاضرة في الوظيفة الواقعية يجب أن يكون لها تصميم مقابل في الوكيل؛ والعناصر الغائبة عن الوظيفة لا يجوز اختلاقها في الوكيل
- كل تحويل يجب أن يرجع لدليل من بحث الوظيفة (المصدر + تاريخ الحصول)
- عنصر وظيفي واحد قد يتحول إلى عدة عناصر للوكيل، لكن كل عنصر للوكيل يجب أن يكون له مصدر وظيفي واحد على الأقل

## 2. مراسي تغطية تصميم الوكيل (0-5)

تقييم كل بُعد من أبعاد تصميم الوكيل بحسب أدلة بحث الوظيفة:

| الدرجة | المستوى | المرساة السلوكية (صياغة عامة) |
|--------|---------|-------------------------------|
| 5 | تغطية كاملة | جميع عناصر الوظيفة مترجمة، ولكل واحد دليل؛ جاهز للتطبيق |
| 4 | تغطية تامة | جميع العناصر الرئيسية مغطاة؛ والتفاصيل قابلة للصقل |
| 3 | تغطية أساسية | الجسم الرئيسي مغطى، لكن هناك نقص صغير واضح (لا معايير قبول / لا مشغّل...) |
| 2 | تغطية جزئية | نحو نصف العناصر مغطاة فقط؛ وعدة أجزاء كُملت «بالحسّ» |
| 1 | تغطية اسمية | البُعد مذكور لكن بلا محتوى قابل للتنفيذ |
| 0 | لا دليل | لا توجد في بحث الوظيفة أدلة تدعم هذا التصميم (لا يعني أنه ممنوع، يعني أنه غير قابل للتحقق) |

**قاعدة الدليل**: لا دليل = 0 درجة مع علامة «بحاجة للتحقق»؛ وبعد بحوث إضافية تُنتج دليلًا يمكن تحديث الدرجات مع الاحتفاظ بتاريخ التقييم.

## 3. أبعاد التصميم الشائعة والأوزان

تُستخرج 5-8 أبعاد تصميم من بحث تصميم الوظيفة، في ثلاث طبقات:

| طبقة الوزن | المعنى | الوزن المقترح | قاعدة الحساب |
|------------|--------|----------------|--------------|
| أساسي (نقض قاطع) | بدونه لا يقوم الوكيل | 0.25-0.35 | الدرجة ≤2 → علامة VETO؛ تُحسب النتيجة لكن الاستنتاج must يُشير إليها |
| مرغوب | يرفع جودة الوكيل بشكل ملحوظ | 0.10-0.20 | يُحتسب طبيعيًا |
| مرجعي | يؤثر في الحكم الهامشي | 0.05-0.10 | يُحتسب طبيعيًا |

**الأبعاد النمطية** (تُخصَّص بحسب الوظيفة، وليست كلها ضرورية):
- أساسية: وضوح الشخصية، وتغطية المسؤوليات، واكتمال سير العمل
- مرغوبة: واجهة تعاون واضحة، ومعايير قبول قابلة للتنفيذ، واكتمال الأدوات
- مرجعية: انضباط صيغة المخرج، وآلية تأريخ الحصول

مجموع الأوزان يجب أن يكون 1.0؛ والعناصر الأساسية عادة 1-2؛ وأكثر من 2 يعني أن التصميم لم يتقارب.

## 4. حساب التغطية والتصنيف

عبر `scripts/match_score.py`: المتوسط المرجّح (0-5) × 20 = نسبة التغطية.

| التغطية | التصنيف | الإجراء |
|---------|---------|---------|
| ≥85 | A جاهز للتطبيق | ابنِ مباشرة كحزمة خبير / مهارة / وكيل فرعي وفق المواصفة |
| 70-84 | B قابل للاستخدام أساسًا | طبّق مع سد نقاط النقص (بحث أو تصميم إضافي) |
| 50-69 | C به نقاط نقص | أكمل البحث أو التصميم أولًا، ثم طبّق |
| <50 | D غير مطابق | عُد إلى الخطوة 2 وأعد دراسة الوظيفة؛ ولا تستعجل التوليد |
| أي عنصر أساسي ≤2 | نقض قاطع | D افتراضيًا مهما كانت النتيجة، إلا بإعفاء صريح من طالب التصميم |

## 5. استخدام match_score.py

```bash
# المُدخل JSON (ملف أو إدخال قياسي)، والمخرج تقرير التغطية
python scripts/match_score.py scores.json
echo '{"dimensions":[{"name":"وضوح الشخصية","weight":0.3,"level":"must","score":4,"evidence":"تعريف الدور واضح: تحليل سلوك المستخدمين وإخراج استنتاجات قابلة للتنفيذ"},{"name":"تغطية المسؤوليات","weight":0.3,"level":"must","score":5,"evidence":"المسؤوليات الستة كلها منقولة إلى خطوات سير العمل"},{"name":"اكتمال الأدوات","weight":0.2,"level":"plus","score":3,"evidence":"سكربت التقييم موجود؛ وأداة قالب التقرير مفقودة"},{"name":"انضباط صيغة المخرج","weight":0.2,"level":"ref","score":2,"evidence":"وصف شفهي فقط؛ ولا قالب محدَّد"}]}' | python scripts/match_score.py
```

صيغة المُدخل:

```json
{
  "dimensions": [
    {
      "name": "وضوح الشخصية",
      "weight": 0.3,
      "level": "must | plus | ref",
      "score": 4,
      "evidence": "تعريف الدور واضح: تحليل سلوك المستخدمين وإخراج استنتاجات قابلة للتنفيذ"
    }
  ]
}
```

المخرج: درجة التغطية الكلية، والتصنيف، وتفاصيل كل بُعد، ونقاط التغطية القوية (≥4)، ونقاط النقص (<3)، وأعلام النقض.

## 6. انضباط الاستخدام

- التقييم يعتمد فقط على أدلة بحث الوظيفة، بلا تخمين؛ وحقل الدليل إلزامي
- جميع أبعاد التصميم للوكيل نفسه تستخدم الأوزان نفسها لضمان القابلية للمقارنة
- عند تحديث بحث الوظيفة تُغيَّر الأدلة أولًا ثم الدرجات؛ بلا «تحريك الهدف حسب الدرجة»
- اذكر دائمًا الثقة جانب درجة التغطية (الأدلة كافية / جزء منها بانتظار التحقق)
- التغطية المنخفضة لا تعني فشل بحث الوظيفة — قد يعني أن أدوار البحث غير كافية: أكمل البحث قبل التصميم
