# Рабочий процесс исследования должностей и генерации агентов

## Назначение

Превратить «хочу создать агента, но не знаю, как его спроектировать» в спецификацию, готовую к внедрению: сначала исследовать, как устроена соответствующая реальная должность, затем поэлементно перевести должностной дизайн в дизайн агента и, наконец, проверить полноту дизайна оценкой покрытия.

## Когда использовать

- Пользователь говорит «не знаю, как сделать агента / подагента / навык» или спрашивает «как спроектировать этого агента»
- Пользователь описывает, что агент должен делать, но не может дать структурированный дизайн
- Пользователь хочет превратить реальную должность в агента
- Пользователю нужна спецификация дизайна для экспертного пакета, отдельного навыка или подагента

## Рабочий процесс из пяти шагов

### Шаг 1: Уточнение потребностей

Выяснить четыре вещи; при нехватке данных — задавать вопросы, никогда не додумывать:

- **Назначение**: что агент будет делать, для кого, кем использоваться?
- **Сценарий**: типовые задачи и входы/выходы?
- **Форма**: экспертный пакет / отдельный навык / подагент (определяет формат спецификации и способ активации)
- **Границы**: что агент явно не делает и какие есть красные линии

### Шаг 2: Исследование дизайна реальной должности

Веб-поиск устройства соответствующей должности с сбором шести элементов. Метод и каналы — в `references/search-playbook.md`:

- **Обязанности**: что человек на этой должности реально делает (до исполнимых действий)
- **Требования**: что делает его компетентным (знания, навыки, опыт, квалификация)
- **Процесс**: реальные шаги работы, их порядок и контрольные точки
- **Взаимодействие**: с кем работает, что передаёт, кто получает результат
- **Метрики**: что значит «сделано хорошо» (качество, эффективность, стандарты результата)
- **Инструментарий**: инструменты, системы и методы

Дисциплина поиска: фиксировать запрос, канал, число попаданий, качество источника и дату получения каждый раунд; каждый вывод подтверждать минимум двумя независимыми источниками; если ничего не найдено — честно сказать и предложить, как расширить поиск; ничего не выдумывать.

### Шаг 3: Должность → агент

Перевод элементов должностного дизайна в элементы дизайна агента; правила маппинга — в `references/capability-matching-model.md`:

| Элемент должности | Элемент дизайна агента |
|------------------|------------------------|
| Роль | frontmatter description + раздел личности |
| Обязанности | список навыков + шаги процесса |
| Требования | анкоры компетенций + красные линии |
| Процесс | шаги рабочего процесса и контрольные точки |
| Взаимодействие | спецификация ввода-вывода и протокол передачи |
| Метрики | критерии приёмки и планки качества |
| Инструментарий | список инструментов и скриптов |

Каждое соответствие должно опираться на доказательства из исследования должности (шаг 2); элементы, отсутствующие в реальной должности, не должны появляться в агенте.

### Шаг 4: Оценка покрытия дизайна

1. Разбить дизайн агента на 5-8 оцениваемых измерений (чёткость личности, покрытие обязанностей, полнота процесса, интерфейс взаимодействия, критерии приёмки, инструментарий, чёткость границ и т.д.)
2. Оценить каждое измерение по доказательствам исследования должности на шкале анкоров 0-5; нет доказательств — нет оценки
3. Запустить `scripts/match_score.py` для взвешенного покрытия (вход: JSON с оценками; выход: итог, grade, сильные позиции, пробелы, флаги вето)
4. Модель оценивания, примеры анкеров и пороги grade — в `references/capability-matching-model.md`
5. По измерениям с пробелами — вернуться к шагу 3 (доп. дизайн) или шагу 2 (доп. исследование) и переоценить

### Шаг 5: Генерация спецификации агента

Следовать `references/report-template.md` для полной спецификации: сначала выводы (что это за агент, основание в должности, grade покрытия), сводка исследования должности (шесть элементов + источники), спецификация дизайна агента (frontmatter, личность, навыки, процесс, инструменты, красные линии, критерии приёмки), детали покрытия с рекомендациями по пробелам, форма внедрения (экспертный пакет / навык / подагент) с шагами активации. Завершить тремя немедленно исполняемыми действиями для пользователя.

## Железные правила

- Исследование должности опирается только на публично доступные источники (JD, материалы оргдизайна, отраслевые отчёты, рассказы практиков); каждый вывод снабжён источником и датой получения; ничего не выдумывается
- Каждый элемент дизайна агента опирается на доказательства из исследования должности; никаких выдуманных способностей
- Не проектировать агентов для мошенничества, обмана, дискриминации, обхода регулирования или нарушения приватности
- Оценки покрытия — только по доказательствам; нет доказательств = 0 баллов и отметка «требует проверки»
- При неясности потребностей — сначала вопросы; никогда не генерировать дизайн на ложных предположениях
