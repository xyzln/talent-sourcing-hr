# Модель маппинга «должность → агент»

> Используется на шагах 3 и 4 навыка `recruit-web-sourcing`. Цель: перевести «должностной дизайн» в «дизайн агента» и проверить полноту дизайна воспроизводимой оценкой покрытия.

## 1. Элементы должностного дизайна → элементы дизайна агента

| Элемент должностного дизайна | Элемент дизайна агента | Где реализуется |
|-----------------------------|------------------------|-----------------|
| Роль (для чего эта должность) | Позиционирование агента | frontmatter description + вступление о личности |
| Обязанности (что делает) | Список навыков и шаги процесса | массив skills + раздел рабочего процесса |
| Требования (что делает компетентным) | Анкоры компетенций и красные линии | ключевые способности личности + железные правила/примечания |
| Процесс (как и в каком порядке) | Шаги процесса и контрольные точки | раздел процесса (у каждого шага есть действия и результат) |
| Взаимодействие (с кем работает) | Спецификация ввода-вывода и протокол передачи | спецификация вывода + условия запуска/выхода |
| Метрики (что значит «сделано хорошо») | Критерии приёмки и планки качества | линия прохода в спецификации вывода |
| Инструментарий (чем работает) | Список инструментов и скриптов | scripts/ + справочники + заметки об инструментах |

**Правила маппинга**:
- Элементы, присутствующие в реальной должности, должны иметь соответствующий дизайн в агенте; элементы, отсутствующие в должности, не должны быть изобретены для агента
- Каждое соответствие должно опираться на доказательства исследования должности (источник + дата получения)
- Один элемент должности может отображаться в несколько элементов агента, но каждый элемент агента должен иметь хотя бы один источник в должности

## 2. Анкоры покрытия дизайна агента (0-5)

Оценка каждого измерения дизайна агента по доказательствам исследования должности:

| Балл | Уровень | Поведенческий анкер (общая формулировка) |
|------|---------|------------------------------------------|
| 5 | Полное покрытие | Все элементы должности переведены, каждый с доказательством; готово к внедрению |
| 4 | Полно | Все основные элементы покрыты; детали можно отполировать |
| 3 | В основном покрыто | Основное тело покрыто, но есть явный мелкий пробел (нет критериев приёмки / триггера и т.п.) |
| 2 | Частично покрыто | Покрыта примерно половина элементов; несколько дописаны «на глаз» |
| 1 | Номинально | Измерение упомянуто, но исполнимого содержания нет |
| 0 | Нет доказательств | В исследовании должности не найдено доказательств, поддерживающих этот дизайн (не значит, что так делать нельзя; значит, что нельзя проверить) |

**Правило доказательств**: нет доказательств = 0 баллов и отметка «требует проверки»; после дополнительного поиска, давшего доказательства, оценки можно обновлять, сохраняя историю оценок.

## 3. Типовые измерения дизайна и веса

Из исследования должности извлекаются 5-8 измерений дизайна в три уровня:

| Уровень веса | Смысл | Рекомендуемый вес | Правило подсчёта |
|--------------|-------|-------------------|------------------|
| Ключевое (жёсткое вето) | Без него агент не работает | 0.25-0.35 | Оценка ≤2 → отметка VETO; итог считается, но вывод обязан её отметить |
| Желательное | Заметно повышает качество агента | 0.10-0.20 | Учитывается обычно |
| Справочное | Влияет на периферийную оценку | 0.05-0.10 | Учитывается обычно |

**Типовые измерения** (адаптировать под должность, не обязательно все):
- Ключевые: чёткость личности, покрытие обязанностей, полнота процесса
- Желательные: чёткий интерфейс взаимодействия, исполнимые критерии приёмки, полный инструментарий
- Справочные: дисциплина формата вывода, механизм отметок времени

Сумма весов должна быть 1.0; ключевых обычно 1-2; больше 2 означает, что дизайн не сошёлся.

## 4. Расчёт покрытия и grade

Через `scripts/match_score.py`: взвешенное среднее (0-5) × 20 = покрытие в процентах.

| Покрытие | Grade | Действие |
|----------|-------|----------|
| ≥85 | A Можно внедрять | Сразу собирать экспертный пакет / навык / подагента по спецификации |
| 70-84 | B В целом работоспособно | Внедрять, параллельно закрывая пробелы (доп. исследование или доп. дизайн) |
| 50-69 | C Есть пробелы | Сначала дозакрыть исследование или дизайн, потом внедрять |
| <50 | D Не подходит | Вернуться к шагу 2 и переисследовать должность; не спешить с генерацией |
| Любой ключевой пункт ≤2 | Жёсткое вето | По умолчанию D независимо от итога, если заказчик явно не сделал исключение |

## 5. Использование match_score.py

```bash
# Вход: JSON (файл или stdin), выход: отчёт о покрытии
python scripts/match_score.py scores.json
echo '{"dimensions":[{"name":"Чёткость позиционирования","weight":0.3,"level":"must","score":4,"evidence":"Определение роли чёткое: анализ поведения пользователей и выводы, пригодные к действию"},{"name":"Покрытие обязанностей","weight":0.3,"level":"must","score":5,"evidence":"Все шесть обязанностей отображены в шаги процесса"},{"name":"Полный инструментарий","weight":0.2,"level":"plus","score":3,"evidence":"Скрипт оценки есть; инструмент шаблона отчёта отсутствует"},{"name":"Дисциплина формата вывода","weight":0.2,"level":"ref","score":2,"evidence":"Только устное описание; шаблон не определён"}]}' | python scripts/match_score.py
```

Формат входа:

```json
{
  "dimensions": [
    {
      "name": "Чёткость позиционирования",
      "weight": 0.3,
      "level": "must | plus | ref",
      "score": 4,
      "evidence": "Определение роли чёткое: анализ поведения пользователей и выводы, пригодные к действию"
    }
  ]
}
```

Вывод: итог покрытия, grade, детали по измерениям, сильные позиции (≥4), пробелы (<3), отметки вето.

## 6. Дисциплина использования

- Оценки — только по доказательствам исследования должности, без додумывания; поле evidence обязательно
- Все измерения одного агента используют один набор весов для сравнимости
- При обновлении исследования должности сначала меняются доказательства, потом оценки; никакого «передвижения планки»
- Всегда указывать уверенность рядом с оценкой покрытия (доказательства достаточны / частично требуют проверки)
- Низкое покрытие не означает провала исследования должности — возможно, не хватило раундов поиска: сначала догоните исследование, потом дизайн
