# 崗位設計研究與智能體生成工作流

## 用途

把「我想造個 agent，但不知道怎么設計」變成一份能直接落地的智能體設計規格：先研究現實中對應崗位是怎麼設計的，再把崗位設計逐項翻譯成 agent 設計，最後用覆蓋度評分驗證設計完整性。

## 使用時機

- 使用者說「不知道怎么做個 agent / 子 agent / 技能」，或問「這個 agent 该怎么設計」
- 使用者描述了想讓 agent 做的事，但給不出結構化的設計
- 使用者想把某個現實崗位 / 角色變成一個 agent
- 使用者需要為專家包、獨立技能或子智能體生成設計規格

## 五步流程

### 第 1 步：需求澄清

確認四件事，缺資訊先提問，不假設：

- **用途**：這個 agent 要干什么活？替誰干？給誰用？
- **場景**：典型任務與輸入輸出是什么？
- **形態**：落地為專家包 / 獨立技能 / 子 agent（決定規格格式與啟用方式）
- **邊界**：明確不做什么、有哪些紅線

### 第 2 步：現實崗位設計研究

全網檢索現實中對應崗位是怎么設計的，采集六大要素。方法與管道見 `references/search-playbook.md`：

- **職責**：這個崗位上的人具體干什么（拆到可執行的動作項）
- **任職要求**：靠什么勝任（知識、技能、經驗、資質）
- **工作流**：真實的工作步驟、順序與檢查點
- **協作介面**：跟誰打交道、交接什么、輸出給誰
- **考核指標**：怎么算干得好（質量、效率、結果標準）
- **工具棧**：用什么工具、系統、方法干活

檢索紀律：每輪記錄檢索式、管道、命中數、信源品質與取得時間；同一結論至少兩個獨立信源交叉驗證；查不到就如實說明並給擴搜建議，不編造。

### 第 3 步：崗位 → 智能體映射

把崗位設計要素逐項翻譯成 agent 設計要素，映射規則見 `references/capability-matching-model.md`：

| 崗位要素 | Agent 設計要素 |
|---------|--------------|
| 角色定位 | frontmatter description 與人格段落 |
| 職責 | 技能清單與工作流步驟 |
| 任職要求 | 能力錨定與邊界鐵律 |
| 工作流 | 工作流步驟與檢查點 |
| 協作介面 | 輸入輸出規格與交接協議 |
| 考核指標 | 驗收標準與品質門檻 |
| 工具棧 | 工具與腳本清單 |

每項映射都必須能回溯到第 2 步的崗位研究證據；崗位上沒有的要素，agent 也不許有。

### 第 4 步：設計覆蓋度評分

1. 把 agent 設計拆成 5-8 個可評分維度（人格定位、職責覆蓋、工作流完整、協作介面、驗收標準、工具完備、邊界清晰等）
2. 按 0-5 級錨定量表對照崗位研究證據打分，無證據不評分
3. 執行 `scripts/match_score.py` 計算加權覆蓋度（輸入評分 JSON，輸出總分、分級、強覆蓋項、缺口項與一票否決標記）
4. 評分模型、錨定範例與分級標準見 `references/capability-matching-model.md`
5. 有缺口的維度，回到第 3 步補設計或回第 2 步補研究，再重評

### 第 5 步：Agent 規格生成

按 `references/report-template.md` 輸出完整規格：結論先行（這個 agent 是什么、崗位依據、覆蓋度分級）、崗位設計研究摘要（六要素 + 信源）、Agent 設計規格（frontmatter、人格、技能、工作流、工具、邊界鐵律、驗收標準）、覆蓋度明細與缺口補齊建議、落地方式（專家包 / 技能 / 子 agent）與啟用步驟。結尾給使用者 3 個可立即執行的下一步動作。

## 鐵律

- 崗位設計研究只依據公開可查信源（JD、組織設計資料、行業報告、從業者分享），所有結論標註信源與取得時間，不編造
- agent 的每項設計必須來自崗位研究證據，不憑空發明能力
- 不設計用於作弊、欺詐、歧視、繞過監管或侵犯隱私的 agent
- 覆蓋度評分只基於證據，無證據 = 0 分並標註「待驗證」
- 需求不清先提問，不在錯誤假設上生成設計
